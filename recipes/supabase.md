# Recipe: Supabase

How each part of the spine in `AGENTS.md` section 5 looks in a Supabase backend: Postgres with Row Level Security, the auto-generated Data API (PostgREST), Supabase Auth, Edge Functions, and Storage. Read the matching section here alongside the skill in `skills/`.

**The one thing that is different about Supabase:** the client talks to the database directly through the Data API. There is no route layer you write. So "at the boundary" in every skill means **the database**: RLS policies, grants, constraints, and RPC functions. Anything you would put in middleware in Express goes into Postgres here, or into an Edge Function when it needs code, a secret, or an outside call.

Installing anything, linking a remote project, `supabase db push`, `supabase functions deploy`, and `supabase secrets set` all need a yes first (`AGENTS.md` section 7).

## What is proven, and what is not

The complete migration in this recipe is `examples/supabase-sql-check/migration.sql`. The SQL excerpts below are copied from it. It was run against real Postgres 18.4 with a stub for Supabase's roles and `auth` schema (`supabase-stub.sql`), and passes 42 checks: RLS isolation, column grants, constraints, audit rows, denial audits that survive commit, role-change rules, the rate limiter, the quota RPC, and the section 13 spine queries. Four deliberate breakages (default grants left on, `raise` instead of `return`, unpinned `search_path`, `using (true)`) were each caught.

Not proven here, because the Supabase CLI needs Docker and none was available: PostgREST behaviour (the pre-request hook registration, error responses, `request.*` settings as PostgREST sets them), Supabase Auth settings, Edge Functions, Storage policies, Realtime, pgTAP via `supabase test db`, and `supabase db lint`. Those sections are written from the Supabase and PostgREST docs and are marked **unproven**. Prove them on the first real project and update this line.

## Layout

```
supabase/
  config.toml             auth settings, rate limits, function config. Committed. No secrets.
  migrations/             timestamped SQL. The only way schema changes.
  functions/
    _shared/              log.ts, reply.ts, clients.ts
    <name>/index.ts       one function per job that needs code, a secret, or an outside call
    .env                  local function secrets. Gitignored.
  tests/                  pgTAP: *.test.sql
  seed.sql                local seed data only. Never real data.
src/types/database.ts     generated by `supabase gen types`
docs/                     prd.md, threat-model.md, secrets.md, adr/
```

Where things go:

| You want to | Put it in |
| --- | --- |
| Let a user read or write their own org's rows | Table + RLS policy + column grants |
| Delete, change a role, export, move money | RPC function (`security definer`), not a direct table grant |
| Call a paid API, send email, verify a webhook, use a secret | Edge Function |
| Store helpers, lookup tables, the audit log | The `private` schema, which is not exposed |

## 1. Keys and secrets → `skills/secrets-handling.md`

| Key | Where it may go | Why |
| --- | --- | --- |
| Project URL | Anywhere | Public |
| Publishable key (`sb_publishable_…`) or legacy `anon` key | Client bundles, mobile apps | Public by design. Everything it can reach must be protected by RLS and grants. |
| Secret key (`sb_secret_…`) or legacy `service_role` key | Edge Functions and trusted servers only | **Bypasses RLS.** Anyone holding it can read and write everything. |
| Database connection string | Migrations and trusted servers only | Contains the database password |
| JWT signing secret (legacy) | Nowhere you control | Lets anyone mint valid user tokens. Prefer asymmetric signing keys. |

Rules for this stack:
- The secret or service-role key never appears in client code, a `NEXT_PUBLIC_` / `VITE_` / `EXPO_PUBLIC_` variable, a mobile app, or a git-tracked file.
- Edge Function secrets are set with `supabase secrets set` (needs a yes) and read with `Deno.env.get()`. Local values live in `supabase/functions/.env`, which is gitignored.
- Secrets the database itself needs (a webhook signing key used by `pg_net`, say) go in Supabase Vault, not in a table or a migration.
- `supabase/config.toml` is committed. It references secrets as `env(NAME)`, never inline values.
- `docs/secrets.md` lists each key, who rotates it, and what needs redeploying afterwards.

```bash
grep -rnE "service_role|sb_secret_|SUPABASE_SERVICE_ROLE_KEY|SUPABASE_SECRET_KEY" --include=*.{ts,tsx,js,jsx,vue,svelte} . | grep -v "^./supabase/functions/"
```

Should print nothing. Any hit outside `supabase/functions/` is a leaked admin key waiting to happen.

## 2. Auth → `skills/auth-spine.md` (partly unproven)

Supabase Auth is **pattern B**: a short-lived access JWT plus a rotating refresh token. Record that in the auth ADR. Do not also build a session-cookie system beside it.

**Settings** (dashboard or `supabase/config.toml`, recorded in the ADR):

| Setting | Beaverdam value | Note |
| --- | --- | --- |
| JWT expiry | 900–3600 s | Supabase default is 3600. `auth-spine.md` asks for 5–15 min; going above 15 min needs a line in the ADR. |
| Refresh token rotation | On | With reuse detection. The reuse interval exists for concurrent tabs; keep it at the default (a few seconds). |
| Minimum password length | 12 | |
| Leaked password protection | On, where the plan allows | Checks against a breached-password list |
| Email confirmation | On | Also stops signup from revealing whether an email exists |
| CAPTCHA (hCaptcha or Turnstile) | On for public signup, sign-in, and reset | Public traffic shapes |
| Session time-box / inactivity timeout | Set, where the plan allows | Maps to the absolute and idle timeouts |
| Signing keys | Asymmetric | Lets servers verify tokens with `getClaims()` without a shared secret |

**Verifying the caller on a server or in an Edge Function:**

```ts
// Verifies signature and expiry. With asymmetric signing keys it checks against the project's JWKS.
const { data, error } = await supabase.auth.getClaims(token);
if (error || !data) return unauthorized();
const userId = data.claims.sub;
```

- Never trust `getSession()` on a server. It reads whatever the cookie or header says without verifying it.
- `getUser(token)` also works. It makes a round trip to the Auth server and catches revoked sessions sooner.

**Never authorize on `user_metadata`.** `raw_user_meta_data` is writable by the user themselves via `auth.updateUser()`. A policy like `auth.jwt() -> 'user_metadata' ->> 'role' = 'admin'` lets anyone make themselves admin. Roles live in a table (section 3). `app_metadata` is only writable with the secret key, but a role in the JWT is still stale until the next refresh.

**Known deviations from `auth-spine.md`, to record in the ADR:**
- With `@supabase/ssr`, tokens are stored in cookies readable by JavaScript, not `HttpOnly`. XSS can steal them. Keep a strict CSP and treat any XSS as an auth incident.
- Login success and failure are recorded by Supabase Auth (auth logs in the dashboard, and `auth.audit_log_entries`), not by `private.audit_log`. Say where each lives in `docs/threat-model.md`.

## 3. RBAC → `skills/rbac.md`

Deny by default. Row Level Security on every table in an exposed schema, Supabase's default grants revoked, and permissions checked by one function that reads the role from a table on every query.

**Private schema.** Helpers and internal tables live here. It is not in the Data API's exposed schemas, so it cannot be queried over HTTP.

```sql
create schema if not exists private;
revoke all on schema private from public;
grant usage on schema private to authenticated; -- RLS policies call private.has_permission()
```

**Role model.** Memberships link users to orgs with a role. The role matrix from `docs/prd.md` is a table.

```sql
create type public.app_role as enum ('member', 'admin', 'owner');

create table public.memberships (
  user_id uuid not null references auth.users(id) on delete cascade,
  org_id  uuid not null references public.orgs(id) on delete cascade,
  role    public.app_role not null,
  primary key (user_id, org_id)
);

-- One row per cell of the role matrix in docs/prd.md.
create table private.role_permissions (
  role       public.app_role not null,
  permission text not null,
  primary key (role, permission)
);
insert into private.role_permissions (role, permission) values
  ('member', 'invoice.read_own'), ('admin', 'invoice.read_own'), ('owner', 'invoice.read_own'),
  ('member', 'invoice.create'),   ('admin', 'invoice.create'),   ('owner', 'invoice.create'),
  ('admin',  'invoice.delete'),   ('owner', 'invoice.delete'),
  ('owner',  'member.role_change');
```

**The one permission check.** `security definer` so it can read `private.role_permissions`. `search_path = ''` so a caller cannot redirect its lookups.

```sql
create function private.has_permission(p_org uuid, p_permission text)
returns boolean
language sql stable security definer set search_path = ''
as $$
  select exists (
    select 1
    from public.memberships m
    join private.role_permissions rp on rp.role = m.role
    where m.user_id = auth.uid() and m.org_id = p_org and rp.permission = p_permission
  );
$$;
revoke all on function private.has_permission(uuid, text) from public;
grant execute on function private.has_permission(uuid, text) to authenticated;
```

Because the role is read from `memberships` on every query, a role change applies on the caller's very next request, with no token refresh. The harness proves this.

**Every table:** enable RLS, revoke Supabase's default grants, grant back only what is needed, then write policies. Leaving the default grants in place is the most common Supabase hole: RLS then becomes the only barrier, and one `using (true)` opens the table to the whole internet.

```sql
create table public.invoices (
  id           uuid primary key default gen_random_uuid(),
  org_id       uuid not null references public.orgs(id),
  customer_id  uuid not null,
  amount_cents integer not null check (amount_cents > 0 and amount_cents <= 100000000),
  currency     text not null check (currency in ('EUR', 'USD')),
  note         text check (char_length(note) <= 500),
  created_by   uuid not null default auth.uid() references auth.users(id),
  created_at   timestamptz not null default now()
);
alter table public.invoices enable row level security;
revoke all on public.invoices from anon, authenticated;
grant select on public.invoices to authenticated;
-- Column list = the allowlist. id, created_by, created_at cannot be set by the client.
grant insert (org_id, customer_id, amount_cents, currency, note) on public.invoices to authenticated;
-- No update or delete grant: deletes go through public.delete_invoice().

create policy invoices_select on public.invoices
  for select to authenticated
  using (private.has_permission(org_id, 'invoice.read_own'));

create policy invoices_insert on public.invoices
  for insert to authenticated
  with check (private.has_permission(org_id, 'invoice.create'));
```

Rules:
- Every policy names its role (`to authenticated`). A policy with no `to` applies to `anon` as well.
- `insert` and `update` policies need `with check`. `using` alone does not stop a user writing a row into another org.
- `anon` gets nothing unless the PRD says a table is public. Then grant `select` only, on named columns.
- Views in `public` are created `with (security_invoker = true)`. Otherwise they run as their owner and skip RLS.
- Never `alter table … force row level security` off, never `using (true)` on user data, never `disable row level security` to make something work.

## 4. Input validation → `skills/input-validation.md`

The database is the boundary, so validation is Postgres types, constraints, and grants. Anything that cannot be said in a constraint goes in an RPC function or an Edge Function.

| Rule | How in Supabase |
| --- | --- |
| Types | Column types: `uuid`, `integer` for money in minor units, `timestamptz`, enums |
| Lengths and ranges | `check (char_length(x) <= n)`, `check (amount > 0 and amount <= …)` |
| Allowed values | `check (x in (…))` or an enum |
| Reject unknown fields / mass assignment | Column-level `grant insert (…)` / `grant update (…)`. Unlisted columns are a permission error. |
| Server-set fields | `default auth.uid()`, `default now()`, and leave them out of the column grant |
| Cross-field and business rules | RPC function with explicit checks, or a trigger |
| Page size | Data API "Max rows" setting (default 1000; lower it), plus `.range()` on the client |
| Anything from outside (webhooks, uploads, third-party responses) | Edge Function with zod, then RPC or insert |

RPC function arguments are typed by Postgres, but check ranges and ownership inside the function. A valid `uuid` is not a permitted `uuid`.

Constraint names reach the client in Data API error messages. Name them plainly (`invoices_amount_cents_check` is fine) and never put data or internals in a constraint name or a `raise exception` message.

## 5. Audit log → `skills/audit-log.md`

Audit rows are written inside the database, in the same transaction as the change, so a rolled-back change leaves no audit row and a committed one always has one.

**The table and the writer.** It lives in `private`, so the API roles cannot read, forge, or delete entries. The harness proves all three.

```sql
create table private.audit_log (
  id            bigint generated always as identity primary key,
  timestamp     timestamptz not null default now(),
  kind          text not null check (kind in ('audit', 'security')),
  request_id    text,
  actor_type    text not null,
  actor_id      text,
  actor_role    text,
  action        text not null,
  resource_type text not null,
  resource_id   text,
  result        text not null check (result in ('success', 'denied', 'error')),
  ip            text,
  route         text,
  detail        jsonb not null default '{}'
);

create function private.audit(
  p_action text, p_resource_type text, p_resource_id text, p_result text,
  p_detail jsonb default '{}'::jsonb, p_kind text default 'audit'
)
returns void
language plpgsql security definer set search_path = ''
as $$
declare
  h jsonb := nullif(current_setting('request.headers', true), '')::jsonb;
  c jsonb := nullif(current_setting('request.jwt.claims', true), '')::jsonb;
begin
  insert into private.audit_log
    (kind, request_id, actor_type, actor_id, actor_role, action, resource_type, resource_id, result, ip, route, detail)
  values (
    p_kind,
    h ->> 'x-request-id',
    case when c ->> 'role' = 'service_role' then 'service'
         when c ->> 'sub' is null then 'anonymous'
         else 'user' end,
    c ->> 'sub',
    c ->> 'role',
    p_action, p_resource_type, p_resource_id, p_result,
    nullif(split_part(coalesce(h ->> 'x-forwarded-for', ''), ',', 1), ''),
    nullif(trim(coalesce(current_setting('request.method', true), '') || ' ' || coalesce(current_setting('request.path', true), '')), ''),
    p_detail
  );
end;
$$;
revoke all on function private.audit(text, text, text, text, jsonb, text) from public;
```

`request.headers`, `request.jwt.claims`, `request.method`, and `request.path` are set by PostgREST for each API request. `actor_role` here is the Postgres role (`authenticated`, `service_role`); the app role is per org, so put it in `detail` where it matters, as `change_member_role` does. The client sets `x-request-id` through `createClient(url, key, { global: { headers: { "x-request-id": id } } })` so its logs and the audit row share one id. It is client-supplied, so it is for correlation only, never trust.

**Row trigger** on every table that holds business data:

```sql
create function private.audit_row()
returns trigger
language plpgsql security definer set search_path = ''
as $$
declare
  v_id      text;
  v_detail  jsonb := '{}'::jsonb;
  v_verb    text := case tg_op when 'INSERT' then 'create' when 'UPDATE' then 'update' else 'delete' end;
begin
  if tg_op = 'DELETE' then v_id := old.id::text; else v_id := new.id::text; end if;
  if tg_op = 'UPDATE' then
    -- Column names only, never values.
    select jsonb_build_object('changed', coalesce(jsonb_agg(n.key), '[]'::jsonb)) into v_detail
    from jsonb_each(to_jsonb(new)) n
    join jsonb_each(to_jsonb(old)) o using (key)
    where n.value is distinct from o.value;
  end if;
  perform private.audit(tg_argv[0] || '.' || v_verb, tg_argv[0], v_id, 'success', v_detail);
  return null;
end;
$$;
revoke all on function private.audit_row() from public;

create trigger invoices_audit
  after insert or update or delete on public.invoices
  for each row execute function private.audit_row('invoice');
```

The trigger expects an `id` column, and the argument is the singular resource name, so actions come out as `invoice.create`, `invoice.update`, `invoice.delete`.

**What a trigger cannot see: denied attempts.** A write blocked by RLS or a grant never reaches the trigger. So anything `audit-log.md` says must be audited "including when denied" (deletes, role changes, exports, payments) is not granted on the table at all. It goes through an RPC that audits the denial itself (section 8).

## 6. Rate limiting → `skills/rate-limit.md`

Three layers, because Supabase has no per-user limit on the Data API out of the box.

**Auth endpoints** use Supabase Auth's built-in limits (sign-ins, sign-ups, token refresh, verification, emails sent), configured in the dashboard or under `[auth.rate_limit]` in `config.toml` (key names vary by CLI version; check the generated file). Set them to the thresholds in `skills/rate-limit.md` and record them in the ADR. Add CAPTCHA on public projects. **Unproven here.**

**Data API writes** use a Postgres limiter registered as PostgREST's pre-request hook, which runs before every API request:

```sql
create table private.rate_limits (
  key          text primary key,
  window_start timestamptz not null,
  hits         integer not null
);

create function private.hit(p_key text, p_limit integer, p_window interval)
returns boolean
language plpgsql security definer set search_path = ''
as $$
declare
  v_hits integer;
begin
  insert into private.rate_limits as r (key, window_start, hits)
  values (p_key, now(), 1)
  on conflict (key) do update set
    hits         = case when r.window_start < now() - p_window then 1 else r.hits + 1 end,
    window_start = case when r.window_start < now() - p_window then now() else r.window_start end
  returning hits into v_hits;
  return v_hits <= p_limit;
end;
$$;
revoke all on function private.hit(text, integer, interval) from public;

create function private.check_request()
returns void
language plpgsql security definer set search_path = ''
as $$
declare
  v_method text := current_setting('request.method', true);
  v_key    text := coalesce(
    auth.uid()::text,
    'ip:' || coalesce(nullif(split_part(coalesce(nullif(current_setting('request.headers', true), '')::jsonb ->> 'x-forwarded-for', ''), ',', 1), ''), 'unknown')
  );
begin
  -- GET/HEAD run in a read-only transaction, so the counter cannot be written there.
  if v_method is null or v_method in ('GET', 'HEAD') then
    return;
  end if;
  if not private.hit('write:' || v_key, 100, interval '1 minute') then
    raise sqlstate 'PGRST' using
      message = '{"code":"rate_limited","message":"Too many requests. Try again later."}',
      detail  = '{"status":429,"headers":{"Retry-After":"60"}}';
  end if;
end;
$$;
revoke all on function private.check_request() from public;
grant execute on function private.check_request() to anon, authenticated;
```

Register it in a migration (needs a yes, like every migration run):

```sql
alter role authenticator set pgrst.db_pre_request = 'private.check_request';
notify pgrst, 'reload config';
```

**Unproven here:** the registration and PostgREST turning `sqlstate 'PGRST'` into an HTTP 429 with `Retry-After` (PostgREST 11+). The function itself is proven: it raises the right error, skips GET, and a blocked request's counter increment is rolled back with the transaction. The count stays at the limit, so the caller stays blocked until the window resets.

`X-Forwarded-For` is only trustworthy as far as Supabase's gateway sets it. The first entry is used here. Treat IP keys as best effort; user keys are the real limit.

**Reads and expensive work** are not covered by the hook (GET is read-only). Bound reads with the Data API max-rows setting and the `authenticated` role's `statement_timeout`. Route anything expensive (exports, search over large sets, paid APIs) through an RPC or Edge Function that takes a quota first:

```sql
create table private.quotas (
  bucket           text primary key,
  limit_per_window integer not null check (limit_per_window > 0),
  window_length    interval not null
);
insert into private.quotas (bucket, limit_per_window, window_length) values
  ('export',     10, interval '1 minute'),
  ('email.send', 20, interval '1 day');

create function public.take_quota(p_bucket text)
returns boolean
language plpgsql security definer set search_path = ''
as $$
declare
  v_limit  integer;
  v_window interval;
begin
  select limit_per_window, window_length into v_limit, v_window from private.quotas where bucket = p_bucket;
  if v_limit is null or auth.uid() is null then
    return false; -- unknown bucket or no caller: deny
  end if;
  -- Returns rather than raises, so the counted hit is kept.
  return private.hit(p_bucket || ':' || auth.uid()::text, v_limit, v_window);
end;
$$;
revoke all on function public.take_quota(text) from public, anon;
grant execute on function public.take_quota(text) to authenticated;
```

For public, high-traffic projects, a table-based limiter adds a write per request. Record in the ADR whether that is acceptable, or whether writes go through an Edge Function backed by Redis.

## 7. Errors

- **Data API errors** go straight to the client as `{ code, message, details, hint }`. You cannot put a handler in front of them, so keep them safe at the source: plain constraint names, and RPC `raise exception` messages written for users. The frontend maps `code` to its own message and never shows `details` or `hint` raw.
- **RPC functions** return a result (`boolean`, a row, or `{ ok, error_code }`) for expected outcomes like "not allowed". Raise only for real errors, and never with internal detail in the message.
- **Edge Functions** use one `reply()` helper (section 9): a safe message plus `request_id` to the client, the detail to the log. No stack traces in responses.
- No empty `exception when others then null;` in plpgsql, and no empty `catch {}` in functions.

## 8. Sensitive actions: RPC only

Delete, role change, export, payment, and anything else that must be audited when denied is not granted on the table. It is a `security definer` function that checks permission, audits every outcome, and then acts.

```sql
create function public.delete_invoice(p_id uuid)
returns boolean
language plpgsql security definer set search_path = ''
as $$
declare
  v_org uuid;
begin
  select org_id into v_org from public.invoices where id = p_id;
  if v_org is null or not private.has_permission(v_org, 'invoice.delete') then
    -- Return, do not raise: an exception would roll back this audit row.
    perform private.audit('invoice.delete', 'invoice', p_id::text, 'denied');
    return false; -- not found and not allowed look the same
  end if;
  delete from public.invoices where id = p_id; -- audit_row records the success
  return true;
end;
$$;
revoke all on function public.delete_invoice(uuid) from public, anon;
grant execute on function public.delete_invoice(uuid) to authenticated;
```

**Return, do not raise, after auditing a denial.** Postgres has no commit inside a function. `raise exception` rolls back the whole transaction, audit row included, so a denied attempt leaves no trace. The harness breaks this on purpose and the denial test fails.

**Revoke `execute` from `public` and `anon` on every function.** Postgres grants `execute` to `PUBLIC` by default, and Supabase grants functions in `public` to `anon` and `authenticated`. A `security definer` function left executable by `anon` is an unauthenticated back door.

Role changes follow the same shape and enforce the rules in `skills/rbac.md`: owners only, the last owner cannot be demoted, every attempt audited with old and new role.

```sql
create function public.change_member_role(p_org uuid, p_user uuid, p_role public.app_role)
returns boolean
language plpgsql security definer set search_path = ''
as $$
declare
  v_old    public.app_role;
  v_owners integer;
  v_res    text := p_org::text || ':' || p_user::text;
begin
  select role into v_old from public.memberships where org_id = p_org and user_id = p_user for update;
  if v_old is null or not private.has_permission(p_org, 'member.role_change') then
    perform private.audit('member.role_change', 'membership', v_res, 'denied');
    return false;
  end if;
  if v_old = 'owner' and p_role <> 'owner' then
    select count(*) into v_owners from public.memberships where org_id = p_org and role = 'owner';
    if v_owners <= 1 then
      perform private.audit('member.role_change', 'membership', v_res, 'denied', jsonb_build_object('reason', 'last_owner'));
      return false;
    end if;
  end if;
  update public.memberships set role = p_role where org_id = p_org and user_id = p_user;
  perform private.audit('member.role_change', 'membership', v_res, 'success',
    jsonb_build_object('old_role', v_old, 'new_role', p_role));
  return true;
end;
$$;
revoke all on function public.change_member_role(uuid, uuid, public.app_role) from public, anon;
grant execute on function public.change_member_role(uuid, uuid, public.app_role) to authenticated;
```

Client call: `const { data: ok, error } = await supabase.rpc("delete_invoice", { p_id: id })`. `ok === false` means not found or not allowed; show one message for both.

## 9. Edge Functions (unproven)

For work that needs code, a secret, or an outside call. Every function follows the same shape: request id, verify the caller, validate input, take a quota if expensive, act as the caller, reply safely.

```ts
// supabase/functions/_shared/http.ts
export function newRequest() {
  const requestId = crypto.randomUUID();
  const log = (level: "info" | "warn" | "error", entry: Record<string, unknown>) =>
    // console.* is the only sink Edge Functions have; this is the one logger. Never log tokens or bodies.
    console[level === "info" ? "log" : level](JSON.stringify({ timestamp: new Date().toISOString(), level, request_id: requestId, ...entry }));
  const reply = (status: number, body: Record<string, unknown>) =>
    new Response(JSON.stringify({ ...body, request_id: requestId }), {
      status,
      headers: { "content-type": "application/json", "x-request-id": requestId },
    });
  return { requestId, log, reply };
}
```

```ts
// supabase/functions/send-invoice/index.ts
import { createClient } from "npm:@supabase/supabase-js@2";
import { z } from "npm:zod@4";
import { newRequest } from "../_shared/http.ts";

const Body = z.strictObject({ invoice_id: z.uuid() });

Deno.serve(async (req) => {
  const { requestId, log, reply } = newRequest();
  try {
    if (req.method !== "POST") return reply(405, { error: "Method not allowed." });

    const token = req.headers.get("Authorization")?.replace(/^Bearer /, "");
    if (!token) return reply(401, { error: "Sign in required." });

    // User-scoped client: every query below runs as the caller, under RLS.
    const supabase = createClient(Deno.env.get("SUPABASE_URL")!, Deno.env.get("SUPABASE_ANON_KEY")!, {
      global: { headers: { Authorization: `Bearer ${token}`, "x-request-id": requestId } },
      auth: { persistSession: false },
    });

    const { data: auth, error: authError } = await supabase.auth.getClaims(token);
    if (authError || !auth) return reply(401, { error: "Sign in required." });

    const parsed = Body.safeParse(await req.json().catch(() => null));
    if (!parsed.success) return reply(400, { error: "Invalid input." });

    const { data: allowed } = await supabase.rpc("take_quota", { p_bucket: "email.send" });
    if (!allowed) return reply(429, { error: "Too many requests. Try again later." });

    // RLS decides whether this caller may see the invoice. No row → same answer as no permission.
    const { data: invoice } = await supabase
      .from("invoices").select("id, amount_cents, currency").eq("id", parsed.data.invoice_id).maybeSingle();
    if (!invoice) return reply(404, { error: "Not found." });

    // Outside call with its own timeout. The API key is a function secret, never sent to the client.
    const res = await fetch("https://api.email-provider.example/send", {
      method: "POST",
      headers: { authorization: `Bearer ${Deno.env.get("EMAIL_API_KEY")}`, "content-type": "application/json" },
      body: JSON.stringify({ template: "invoice", invoice_id: invoice.id }),
      signal: AbortSignal.timeout(5000),
    });
    if (!res.ok) throw new Error(`email provider responded ${res.status}`);

    log("info", { kind: "audit", actor: { type: "user", id: auth.claims.sub }, action: "invoice.send", resource: { type: "invoice", id: invoice.id }, result: "success" });
    return reply(202, { ok: true });
  } catch (err) {
    log("error", { kind: "app", message: String(err) });
    return reply(500, { error: "Something went wrong." });
  }
});
```

Rules:
- Default to the user-scoped client. Create a secret-key client only for the specific statement that needs to bypass RLS, keep it inside the function, and say why in a comment.
- Audit rows for actions that only happen in a function go to the function log as above. If the action must be queryable with the rest of the audit trail, call an RPC that writes `private.audit_log` instead.
- **Webhooks** from third parties: set `verify_jwt = false` for that function in `config.toml`, verify the provider's signature on the raw body (`await req.text()`) before parsing, check the timestamp tolerance, then validate with zod. A webhook function with `verify_jwt = false` and no signature check is a public write endpoint.
- `verify_jwt` behaviour differs between legacy JWT secrets and the newer signing keys. Verifying in code with `getClaims()`, as above, works either way.

## 10. Storage (unproven)

- Buckets are private (`public = false`) unless the PRD names public files. Set `file_size_limit` and `allowed_mime_types` on every bucket.
- Paths are `<org_id>/<generated-uuid>.<ext>`. Never the user's filename.
- Policies on `storage.objects` reuse the permission function:

```sql
create policy invoice_files_read on storage.objects
  for select to authenticated
  using (bucket_id = 'invoice-files'
         and private.has_permission(((storage.foldername(name))[1])::uuid, 'invoice.read_own'));

create policy invoice_files_upload on storage.objects
  for insert to authenticated
  with check (bucket_id = 'invoice-files'
              and private.has_permission(((storage.foldername(name))[1])::uuid, 'invoice.create'));
```

- Hand out files with short-lived signed URLs (`createSignedUrl(path, 60)`), not public URLs.

## 11. Realtime (unproven)

- Postgres Changes respects RLS on the table, but only for tables you add to the `supabase_realtime` publication. Add only what clients need.
- Broadcast and Presence: use private channels (`supabase.channel(name, { config: { private: true } })`) and write RLS policies on `realtime.messages` that call `private.has_permission`. Turn off public channel access in the project's Realtime settings.
- Channel names carry the org id (`org:<uuid>:invoices`) so the policy can check it.

## 12. Backend-shape extras → `skills/backend-shape.md`

- **Transactional:** an RPC function is one transaction, so multi-step writes go in one RPC. Idempotency: an `idempotency_keys` table with `primary key (user_id, key)`, checked and written inside the same RPC (same flow as the Node recipe, section 12). Outbox: insert into an outbox table (or a Supabase Queue, which is `pgmq`) inside the RPC; an Edge Function on a schedule drains it. Never call a payment provider from inside a database function.
- **Analytics:** reporting views with `security_invoker = true`, read through an RPC that takes the `export` quota and writes a `data.export` audit row. Heavy reads go to a read replica if the plan has one.
- **Real-time:** section 11.
- **Public, high traffic:** lower max rows, a tighter `statement_timeout` on `authenticated`, CAPTCHA on auth, and an ADR on whether the table-based limiter holds.

**Spine checks as a test.** Run these in pgTAP (`select is((select count(*) from (<query>) q), 0::bigint, '<name>')`) or as plain queries. Each must return no rows. These exact queries are in the harness.

```sql
-- every table in public has RLS
select c.relname from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind in ('r','p') and not c.relrowsecurity;

-- anon holds no privilege on any public table or view
select c.relname from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind in ('r','p','v','m')
  and has_table_privilege('anon', c.oid, 'select,insert,update,delete');

-- anon can execute no public function
select p.proname from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and has_function_privilege('anon', p.oid, 'execute');

-- every security definer function pins search_path
select n.nspname || '.' || p.proname from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where p.prosecdef and n.nspname in ('public','private')
  and not exists (select 1 from unnest(coalesce(p.proconfig, '{}')) cfg where cfg like 'search_path=%');

-- no public view runs as its owner
select c.relname from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'v'
  and not coalesce(c.reloptions @> array['security_invoker=true'], false);

-- API roles cannot touch private tables
select c.relname from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'private' and c.relkind = 'r'
  and (has_table_privilege('authenticated', c.oid, 'select,insert,update,delete')
    or has_table_privilege('anon', c.oid, 'select,insert,update,delete'));
```

Adjust the anon checks if the PRD makes a table or function public on purpose, and name the exception in the test.

## 14. Checks before merge

The pre-merge checklist in `AGENTS.md` section 6, for this stack:

- [ ] `supabase test db` passes, including the spine checks. Paste the output.
- [ ] `supabase db lint` shows no security warnings (RLS disabled, security definer view, mutable search_path). Paste the output.
- [ ] Every new table: RLS on, default grants revoked, column-level grants, policies with `to authenticated`, `with check` on writes, audit trigger.
- [ ] Every new function: `security definer` only if needed, `set search_path = ''`, `execute` revoked from `public` and `anon`, denial audited with `return` not `raise`.
- [ ] No authorization on `user_metadata`.
- [ ] The secret-key grep from section 1 prints nothing. Secret scan passes.
- [ ] Every new Edge Function verifies the caller (or the webhook signature), validates with zod, takes a quota if expensive, and replies through `reply()`.

## When this recipe is out of date

Supabase changes quickly: API key formats, JWT signing, Auth settings, and CLI config keys have all moved recently. If a project hits a setting, key name, or API here that no longer exists, stop. Do not guess a replacement for anything in sections 1, 2, 3, 5, or 8 (keys, auth, RBAC, audit, sensitive RPCs). Tell the human, then fix this file with what changed and when. Re-run `examples/supabase-sql-check` after any change to the SQL here.

`AGENTS.md` section 7 outranks this recipe wherever they disagree.
