# Auth Spine

One auth pattern per project, chosen from a short approved list and recorded in an ADR. No ad hoc reinvention, no second pattern bolted on later without a decision.

**Read when:** building or changing login, signup, logout, sessions, tokens, password reset, or anything that decides who the caller is.

## Rule

- Choose exactly one pattern from the approved list. Record it as an ADR before the first auth endpoint.
- Anything outside the list needs its own ADR and explicit human approval before code: client-mandated SSO (SAML, OIDC provider), magic links, passkeys, API keys for machine callers, third-party auth providers.
- Using a managed provider (Supabase Auth, Auth0, Clerk) still means choosing one of the two patterns below for how the backend verifies the caller. The provider does not replace the rules.
- No recipe for the stack yet: propose the pattern in the stack's code and wait for approval. Auth is never improvised.

## Approved patterns

### A. Session cookie + CSRF protection

Best for: a web app served from the same site as the API.

- Session id is random, at least 128 bits, generated by a vetted library. Stored server-side (DB or shared store), not as a self-contained token.
- Cookie flags: `HttpOnly`, `Secure`, `SameSite=Lax` (or `Strict` if nothing cross-site links in), `Path=/`. No `Domain` wider than needed.
- CSRF: every state-changing request (POST, PUT, PATCH, DELETE) is protected by a CSRF token or a double-submit cookie, plus an `Origin` header check. `SameSite` alone is not enough.
- Regenerate the session id on login and on privilege change.
- Idle timeout and absolute timeout, both documented. Defaults: 30 minutes idle, 12 hours absolute, unless the PRD says otherwise.
- Logout deletes the server-side session, not only the cookie.

### B. Short-lived access token + refresh token

Best for: mobile apps, third-party clients, or an API on a different site from the frontend.

- Access token lifetime: 5–15 minutes. Refresh token lifetime: documented, default 7–30 days.
- If access tokens are JWTs: pin the algorithm server-side and reject `none`; verify signature, `exp`, `iss`, and `aud` on every request; keep claims minimal (user id, role, session id) and never put personal data in them.
- Refresh tokens are opaque, stored hashed server-side, and **rotated on every use**. If a used refresh token is presented again, revoke the whole token family and log it as a security event.
- Web clients keep the refresh token in an `HttpOnly`, `Secure` cookie, not in `localStorage`. Mobile clients use the platform keychain or keystore.
- Logout and password change revoke the refresh token family server-side.

## Rules for both patterns

- **Passwords:** hash with argon2id (preferred) or bcrypt. Never a fast hash, never reversible encryption. Enforce a minimum length (default 12), check against a breached-password list if the stack has a vetted library for it, no maximum below 64 characters.
- **Login errors:** one generic message for wrong email and wrong password. Same response time either way where practical. No account enumeration via signup or reset either.
- **Password reset:** single-use token, at least 128 bits random, stored hashed, expires within 1 hour, invalidated on use and on password change. Revokes existing sessions.
- **Rate limits:** login, signup, reset, and refresh are rate limited per `rate-limit.md`.
- **Audit:** login success, login failure, logout, password change, reset request, reset completion, and refresh-token reuse each write an audit entry per `audit-log.md`. Never log the password or the token.
- **Verification of identity happens server-side on every request.** A user id in the request body, query, or a client-set header is never trusted as identity.

## Flag before writing

- A second auth mechanism appearing in a project that already has one.
- Tokens or session ids in URLs, logs, or error responses.
- JWT verification that skips `exp`, `aud`, or algorithm pinning.
- Auth checked in the frontend only.
- A "skip auth in dev" flag, test user, or master password that could reach production.
- Hand-rolled crypto, token generation with a non-cryptographic random, or string comparison of secrets that is not constant-time.

## Done when

- [ ] ADR records the chosen pattern, lifetimes, and timeouts
- [ ] Tests: valid credentials, wrong password, unknown user (same response), expired session or token, revoked session or token, CSRF missing (pattern A), refresh reuse (pattern B)
- [ ] Auth endpoints rate limited and audited
- [ ] No token, session id, or password in any log line (checked, not assumed)

`AGENTS.md` section 7 outranks this doc wherever they disagree. Changing the auth pattern always needs an ADR and approval.
